== what is concurrency

Concurrency in computer science refers to the +
**ability of different parts of a program to execute independently and simultaneously**.

=== !

It enables multiple computations to +
**progress at the same time**, +
either by allowing different parts of a program to be +
**executed out of order** +
or +
**simultaneously on multiple processors**

== why concurrency matters

[quote,,Herb Sutter]
There are two major reasons for which concurrency, especially multithreading, is already used in mainstream software. +
The first is to logically separate naturally independent control flows; for example, in a database replication server
I designed it was natural to put each replication session on its own thread, because each session worked completely
independently of any others that might be active (as long as they weren’t working on the same database row).

=== !

[quote,,Herb Sutter]
The second and less common reason to write concurrent code in the past has been for performance,
either to scalably take advantage of multiple physical CPUs or to easily take advantage of latency in other parts of the application; in my
database replication server, this factor applied as well and the separate threads were able to scale well on multiple CPUs as our server
handled more and more concurrent replication sessions with many other servers

=== concurrency is hard

[quote,,Herb Sutter]
Probably the greatest cost of concurrency is that concurrency really is hard: The programming model, meaning the model in the programmer’s
head that he needs to reason reliably about his program, is much harder than it is for sequential control flow.

=== !

[quote,,Herb Sutter]
Everybody who learns concurrency thinks they understand it, ends up finding mysterious races they thought weren’t possible, and discovers
that they didn’t actually understand it yet after all. As the developer learns to reason about concurrency, they find that usually those races can
be caught by reasonable in-house testing, and they reach a new plateau of knowledge and comfort

=== why it is so hard?

* software developers don't care about hardware any more (aka cloud computing)
* the programming model in the programmer’s head that he needs to reason reliably about his program, is much harder than it is for sequential control flow (aka our brains are single threaded)
* your code doesn't translate to set of instructions that gets executed on the CPU, compilers and CPU can reorder instructions (aka illusion of execution)

== happens before relation

image::https://media0.giphy.com/media/v1.Y2lkPTc5MGI3NjExZnViY2gxc2Q3M2Y3MmMyb2hhdW1iMWw2MWk4aDI0azdtOWs0Y2doNSZlcD12MV9pbnRlcm5hbF9naWZfYnlfaWQmY3Q9Zw/AROZBEIVlt6vu/giphy.gif[background]

=== !

When we say "A happens before B" +
it means that *all actions* and *memory changes* +
in A are guaranteed to be visible to B

=== !

If thread 1 writes to a variable and thread 2 reads it later, +
without proper "happens before" relationship, +
thread 2 might see an old/stale value

=== safe publication

in other words

[quote,Safe Publication and Safe Initialization in Java,Aleksey Shipilёv]
Safe publication differs from a regular publication on one crucial point. Safe publication makes all the values written before the publication visible to all readers that observed the published object. It is a great simplification over the JMM rules of engagement with regards to actions, orders and such.

=== !

This is why we can't just use regular variables shared between threads +
as read and write actions on these variables don't establish "happens before" +
and are not immune to hardware optimizations and memory ordering for your CPU

=== !

* Java Memory Model defines pairs of actions that establish "happens before" relationship
** volatile read followed by volatile write
** synchronized enter and exit
** lock acquire and release
** and many more

=== object pool

A thread-safe object pool implementation

* With minimum and maximum capacity
* The pool auto-creates objects up to maximum capacity and maintains minimum number of valid objects
* Invalid objects are replaced to maintain minimum capacity

=== properties

* only n threads can access the pool at the same time
* resource can be borrowed only by single thread at a time

=== implementation

* `Semaphore` to control how many threads can access the pool at the same time
* `Queue` to store objects

=== !

but, how to make sure it is thread-safe? +

my approach is based on heuristics not on formalisms, +
results may vary

=== !

* write single-threaded tests first, to verify correctness
* write multi-threaded jcstress tests, to verify thread-safety
* write jmh microbenchmarks, to verify performance

=== expected behaviors?

* identify shared state
* identify actions that access state and can be performed from multiple threads
* find out what happens before relationship is established between these actions
* write down expected behaviors for each pair of actions, for both cases when A happens before B and when B happens before A

=== actor model

The actor model is a conceptual framework for building concurrent systems where actors serve as the fundamental unit of computation.

Each actor is an independent entity that processes messages asynchronously through its dedicated mailbox, which acts as a message queue.

Actors communicate exclusively by sending messages to each other's mailboxes, never sharing state directly.

=== !

When an actor receives a message, it can:

* perform local computations
* create new actors
* send messages to other actors
* modify its own internal state

=== !

This message-passing approach naturally enforces isolation and encapsulation, making concurrent systems:

* easier to reason about
* less prone to deadlocks
* less prone to race conditions

=== !

The model achieves concurrency through parallel message processing, where multiple actors can process their respective messages simultaneously without interfering with each other.

=== properties

* Each actor has its own mailbox, which is a queue of messages
* Actor processes single message at a time
* Actors are running on shared thread pool, to avoid creating actor per thread

=== implementation

* Actors are executed on a thread pool, using `ExecutorService`
* Each actor has its own mailbox implemented as `Queue`
* Use `AtomicBoolean` to signal actor is processing a message

=== mapreduce

MapReduce is a programming paradigm designed for processing and generating large datasets in parallel.
The algorithm consists of two core phases executed in sequence - map and reduce.

=== map phase

During the map phase, input data is partitioned and distributed across multiple worker nodes or threads. +
Each worker transforms its chunk of data by applying a map function that processes individual records. +
The map function emits key-value pairs which are then grouped by key.

=== reduce phase 

In the reduce phase, grouped key-value pairs are processed in parallel by reduce workers. +
Each reducer receives all values associated with a particular key and combines them into a final result. +
Multiple reducers can work simultaneously on different keys, enabling parallel processing.

=== intermediate phase

Between map and reduce phases, the framework performs an important shuffle and sort operation. +
This phase groups and sorts all key-value pairs with the same key from different mappers. +
The sorting ensures reducers receive their input values in a deterministic order.

(for simplicity will skip this one)

=== properties

* input data is partitioned and distributed across multiple workers
* reducing phase needs to wait for mapping phase to complete
* mapping and reducing are executed in parallel
* intermediate results are stored in memory

=== implementation

* use `ExecutorService` to execute map and reduce tasks
* use `Phaser` barrier to synchronize map and reduce phases
* use `ConcurrentHashMap` to store intermediate results

=== worth noting

* `CyclicBarrier` and `CountDownLatch` are not suitable for this use case, because we don't know how many entries we will process
* `Phaser` is a better choice because it allows us to wait for multiple phases to complete
* `Phaser` can for a DAG (direct acyclic graph) of tasks, where each task can depend on the completion of previous tasks
* `compute*` operations in `ConcurrentHashMap` are performed atomically. Some attempted update operations on this map by other threads may be blocked while computation is in progress, so the computation should be short and simple, and must not attempt to update any other mappings of this map.

== pubsub

A pubsub is a messaging system that allows publishers to send messages to one or more subscribers. +

Subscribers can subscribe to specific topics or patterns, and the pubsub system ensures that messages are delivered to the correct subscribers. +

Let's implement in memory pubsub, modeled after Kafka, with consumer groups and offset tracking.

=== properties

* messages are published to a topic
* subscribers can subscribe to a topic
* subscribers can receive messages from a topic
* subscribers track their offset in the topic

=== implementation

* use ConcurrentHashMap to store topics
* use StampedLock to synchronize access to messages

== cache

A cache implementation that uses LRU (Least Recently Used) eviction policy.
When an entry is not found in the cache, it can automatically load it from the backing store.

=== properties

* uses a non-blocking approach with fine-grained locking for optimal performance under high contention
* doesn't use background threads for eviction, rather uses piggy-backing on put/get operations

=== implementation

* `ConcurrentHashMap` to store entries
* double-linked list to store entries in the order of their last access, implemented using `AtomicReference`
* `ReentractLock` to synchronize access to the cache
