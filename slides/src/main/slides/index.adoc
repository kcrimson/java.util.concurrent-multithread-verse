== Java Memory Model

its formal specification is complex +
once you understand it, +
you loose ability to explain it to others +
(aka Aleksey Shipilëv paradox)

=== !

sequentially consistency in absence of data races

transitive closure (from set theory) of:

* program order
* synchronization order
* synchronizes-with relation
* happens-before relation

=== !

it is simple as long as you focus on effects +
not on formalisms and implementation details

I made this mistake few years ago

=== here is my story

* read https://gee.cs.oswego.edu/dl/jmm/cookbook.html[The JSR-133 Cookbook for Compiler Writers by Doug Lee], **DON'T DO IT**, this is for language designers and compiler writers, fallen into trap of memory barriers
* **NOTICE** this article outdated, read https://gee.cs.oswego.edu/dl/html/j9mm.html[Using JDK 9 Memory Order Modes by Doug Lea]

=== !

* did few months break from memory models, got into JVM internals in meantime :)
* somebody in my close circle recommended me to read  https://shipilev.net/blog/2016/close-encounters-of-jmm-kind/[Close Encounters of The Java Memory Model Kind by Aleksey Shipilëv]

=== !

* read Java Memory Model Pragmatics, few "aha" moments,

few important takeaways

* never, ever, give up
* if you are not a compiler writer, formalisms are not for you
* focus on effects, and implementation details will come later
* people designing these things are not the best one to explain it
* multicore CPUs are distributed systems on a chip

== happens before relation

When we say "A happens before B" +
it means that all *actions* and *memory changes* +
in A are guaranteed to be visible to B

=== !

If thread 1 writes to a variable and thread 2 reads it later, without proper "happens before" relationship, thread 2 might see an old/stale value

=== !

This is why we can't just use regular variables shared between threads - they don't establish "happens before" and are not immune to hardware optimizations and memory ordering for your CPU

=== !

* Java Memory Model defines pairs of actions that establish "happens before" relationship
** volatile write followed by volatile read
** synchronized enter and exit
** lock acquire and release
